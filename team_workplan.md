# План работ команды (2 участника) — Budget-Aware Coding Agent Harness

Документ описывает распределение ролей, единый контракт взаимодействия модулей, пошаговый бэклог задач и чек-лист перед финальной сдачей, чтобы оба разработчика могли работать параллельно без конфликтов в Git.

## 1. Разделение зон ответственности по папкам

Чтобы избежать merge-конфликтов, репозиторий разделён на два независимых контура, стыкующихся через `harness/config.py`:

| Параметр | Участник 1 (Роль: Agent Core & Domain Solvers) | Участник 2 (Роль: Planner, ML Estimator & DevOps) |
| :--- | :--- | :--- |
| **Рабочая ветка Git** | `feat/agents-core` | `feat/planner-estimator` |
| **Зона файлов в репозитории** | `harness/agents/*`, `harness/sandbox/*` | `harness/planner/*`, `scripts/*`, `Dockerfile`, `run_agent.py`, `trajectories/*` |
| **Главная цель** | Решать задачу за **минимальное число токенов** и **не ломать тесты**, грамотно переключая 4 модели Qwen и компоненты [openJiuwen](https://github.com/openJiuwen-ai/agent-core). | **Отсеивать 15–25% невыполнимых задач** за 0 токенов, точно предсказывать цену задачи `E[tokens]` и максимизировать сумму `reward` в очереди. |
| **Точка входа / интерфейс** | Функция `async def solve_task(ctx: TaskContext, config: HarnessConfig) -> SolveResult` в `harness/agents/base_harness.py`. | Класс `TaskScheduler` в `harness/planner/scheduler.py`, вызывающий `solve_task` для отобранных задач. |

## 2. Неприкосновенный контракт стыковки (`harness/config.py`)

Оба участника используют структуры `TaskContext` и `SolveResult` из `harness/config.py`. Если нужно добавить новое поле — добавляйте его со значением по умолчанию (`default`), чтобы не ломать код напарника:

- **Что Планировщик (Участник 2) передаёт в `solve_task(ctx, config)`:**
  - `ctx.task_id` — идентификатор задачи (например, `coding_0003`);
  - `ctx.task_type` — определённый тип (`coding`, `data_analysis`, `math`, `search`);
  - `ctx.instruction` — текст задания из `task.json`;
  - `ctx.reward` — стоимость задачи в баллах;
  - `ctx.task_dir` и `ctx.workspace_dir` — пути к папке задачи и её файлам;
  - `ctx.max_token_budget` — максимально допустимый расход приведённых токенов на эту задачу;
  - `ctx.allow_reasoning_escalation` — `True`, если награда высокая и при фейле первой попытки разрешено включить reasoning-модель (`qwen3.8-27b`).

- **Что Агент (Участник 1) возвращает в `SolveResult`:**
  - `status` — строго одно из значений: `"SOLVED"`, `"UNSOLVABLE"`, `"BUDGET_EXCEEDED"`, `"FAILED"`;
  - `answer` — готовая чистая строка для записи в `answer.txt` (например, `"DONE"`, `"158"`, `"Osaka"`);
  - `input_tokens`, `output_tokens`, `reasoning_tokens` — фактический расход токенов за все вызовы внутри задачи (формула `effective_cost = input/10 + output + reasoning` считается автоматически).

### Этап 2: Расширение тренировочного датасета и детекция невыполнимых задач (Часы 4–10)

#### Задачи Участника 1 (Agent Core & Solvers)
- [ ] **Усиление `coding_solver.py`:**
  - Поддержать задачи, где в `workspace/` несколько `.py` файлов или вложенные пакеты.
  - Если в `coding`-задаче падает только 1 тест из 6, передавать в промпт код модуля и точный `AssertionError`, чтобы модель не ломала уже работающие функции.
  - Добавить проверку неизменности `test_*.py` (контрольная сумма SHA256 до и после патча), чтобы модель не «читерила» модификацией тестов ([ImpossibleBench](https://arxiv.org/abs/2510.20270)).
- [ ] **Усиление `search_solver.py`:**
  - Расширить локальный графовый резолвер в `_parse_kb()` на 3-hop запросы (например, `Person -> Mentor -> Employer -> Headquarters` или фильтрацию по году основания компании `Founded` / году рождения `Born`), чтобы решать максимум `search`-задач за **0 токенов**.
- [ ] **Усиление `data_solver.py`:**
  - Добавить авто-проверку результата Python-скрипта: если скрипт вернул `NaN`, `None`, пустую строку или `Traceback`, делать 1 короткий ретрай с текстом ошибки в `qwen3.8-27b-noreason`.

#### Задачи Участника 2 (Planner, Estimator & Docker)
- [ ] **Доработка `scripts/generate_dataset.py`:** Сгенерировать полноценный тренировочный пул на **200 задач** (по 50 задач каждого из 4 типов), из которых **40 задач (20%) заведомо невыполнимы**:
  - *Невыполнимые `coding`:* конфликтующие ассерты в `test_mylib.py`, отсутствие вызываемой тестом функции при запрете её угадывания, бесконечная рекурсия во входных данных.
  - *Невыполнимые `search`:* вопрос про человека/компанию, которых нет в `kb/`, циклическая ссылка `Mentor A -> Mentor B -> Mentor A`, отсутствие поля `Headquarters` в карточке компании.
  - *Невыполнимые `data_analysis`:* запрос по несуществующему продукту/региону (если по смыслу вопроса ответ не может быть `0`) или отсутствие нужной колонки в CSV.
  - *Невыполнимые `math`:* деление на `0`, отрицательное число коробок при физическом ограничении или неполное условие.
- [ ] **Расширение `harness/planner/unsolvable_filter.py`:** Добавить Zero-Token эвристики под все перечисленные паттерны невыполнимости, чтобы отсекать их до вызова LLM.
